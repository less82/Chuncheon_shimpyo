# 쉼표 정류장 제로베이스 재구축 필수요건

> 작성 기준일: 2026-07-25  
> 목적: 쉼표 정류장을 시연용 화면이 아닌 실제 운영 가능한 서비스로 처음부터 다시 설계할 때 필요한 기능, 데이터, API, 시스템, 운영 기준을 한 문서에서 검토한다.

---

## 0. 결론부터 보기

쉼표 정류장의 핵심은 다음 두 흐름이다.

1. **시민 이동 흐름**  
   출발지·목적지 입력 → 장소 확인 → 탈 정류장·방면·버스 탐색 → 실시간 도착정보 확인
2. **정류장 관리 흐름**  
   시민 제보 → AI 보조 분류 → 담당자 검수 → 현장 확인 → 시설 정보 갱신

운영 가능한 최소 제품을 만들기 위해 아래 8개는 반드시 필요하다.

| 번호 | P0 필수 항목 | 완료 기준 |
|---:|---|---|
| 1 | 정류장·노선 마스터 | 정류장과 노선의 내부 기본키, 좌표, 방면, 정류장 순서를 확정한다. |
| 2 | 외부 ID 매핑 | 내부 관리번호, 경로 공급자 ID, TAGO 노드 ID를 방면까지 검증한다. |
| 3 | 장소 검색 | 춘천시 장소를 검색하고 사용자가 지도·주소로 확정할 수 있다. |
| 4 | 대중교통 경로 탐색 | 출발지·목적지에서 올바른 승차·하차 정류장과 노선을 계산한다. |
| 5 | 실시간 도착정보 | TAGO를 서버에서 조회하고 실패 시 추정값을 만들지 않는다. |
| 6 | 시민 API·DB | 외부 API 키를 숨기고 경로·도착·정류장 정보를 일관된 형식으로 제공한다. |
| 7 | 제보·관리자 시스템 | 제보를 영구 저장하고 담당자가 인증 후 검수·처리할 수 있다. |
| 8 | 검수·감사·모니터링 | 데이터 변경 이력, 관리자 작업, API 장애를 추적하고 롤백할 수 있다. |

AI, 예산 시뮬레이션, 화려한 통계 대시보드는 위 8개를 갖춘 뒤에 개발한다.

### 1.3 제품에서 금지할 동작

- 동명 정류장을 이름만으로 자동 선택하지 않는다.
- 맞은편 정류장의 시설을 합산하지 않는다.
- 경로가 없을 때 가까운 정류장을 임의로 추천하지 않는다.
- 배차간격을 실시간 도착예정시간처럼 표시하지 않는다.
- 실시간 조회 실패를 추정 도착시간으로 숨기지 않는다.
- 근거 없는 시설 상태를 `없음`으로 생성하지 않는다.
- 조회 수나 제보 수를 승차량·고령자 수요·수혜 인원으로 표현하지 않는다.
- 공식 민원 시스템과 연계하기 전에는 `민원 접수`라고 표시하지 않는다.
- AI가 정류장 ID, 시설 상태, 공사 여부, 예산을 자동 확정하지 않는다.

### 2.2 정류장 마스터 필수 필드

| 필드 | 설명 | 규칙 |
|---|---|---|
| `management_id` | 내부 정류장 기본키 | 변경하지 않는 고유값 |
| `stop_no` | 현장 표지판 번호 | 중복·미표기 가능성을 고려 |
| `name` | 정류장 표시명 | 기본키로 사용 금지 |
| `lat`, `lng` | WGS84 좌표 | 범위·이상치 검사 |
| `direction_text` | 정류장 진행 방면 | 맞은편 정류장 구분에 필수 |
| `operation_status` | 운영·휴지·폐지 상태 | 유효기간과 함께 관리 |
| `valid_from`, `valid_to` | 데이터 유효기간 | 이설·폐지 이력 보존 |
| `source_id` | 원본 레코드 식별자 | 원본 추적 가능해야 함 |
| `verified_at` | 마지막 검수일 | 검수자와 함께 저장 |

### 2.3 외부 ID 매핑 필수 필드

```text
management_id
provider
provider_stop_id
direction_text
lat
lng
match_status
match_method
source_record_id
verified_by
verified_at
valid_from
valid_to
```

매핑 상태:

- `verified`: 공식 대응표 또는 사람이 번호·좌표·방면까지 검증
- `inferred`: 규칙으로 추론했지만 사람이 미검수
- `unresolved`: 일치 후보를 확정할 수 없음

운영 경로·도착정보에는 `verified` 매핑만 사용한다.

### 2.4 시설 데이터 계약

시설 종류:

- 의자 `seat`
- 그늘막·쉘터 `shade`
- 야간조명 `light`
- 도착정보안내기 `sign`

각 시설은 다음 구조로 저장한다.

```json
{
  "facilityType": "seat",
  "status": "yes",
  "sourceType": "official_registry",
  "sourceRecordId": "source-123",
  "observedAt": "2026-07-01",
  "verifiedBy": "user-id",
  "validFrom": "2026-07-01",
  "validTo": null
}
```

상태 규칙:

| 상태 | 의미 | 사용 조건 |
|---|---|---|
| `yes` | 있음이 확인됨 | 공식 대장 또는 검수된 관측 근거가 있음 |
| `no` | 없음이 확인됨 | 현장조사 등으로 부재를 직접 확인함 |
| `unknown` | 확인되지 않음 | 근거가 없거나 오래돼 현재 상태를 확정할 수 없음 |

- [ ] 응답 데이터 저장·캐시가 약관상 허용되는가?
- [ ] 서버 호출과 도메인·IP 제한을 지원하는가?
- [ ] 공급자 교체가 가능하도록 내부 응답 규격을 분리했는가?

공개 Nominatim 서버와 OSRM 데모 서버는 운영 기반으로 사용하지 않는다.

## 4. 자체 API 설계

### 4.1 시민 API

| 메서드·경로 | 역할 | 주요 응답 |
|---|---|---|
| `GET /v1/places/search?q=` | 춘천시 장소 검색 | 장소명, 주소, 좌표, 공급자 ID |
| `POST /v1/trips/search` | 대중교통 경로 탐색 | 승하차 정류장, 노선, 방면, 도보시간 |
| `GET /v1/stops/{id}` | 정류장 상세 | 번호, 방면, 좌표, 시설 상태와 근거 |
| `GET /v1/stops/{id}/arrivals` | 실시간 도착 조회 | 노선, 도착 초, 이전 정류장 수, 조회 시각 |
| `POST /v1/reports` | 정류장 상태 제보 | 접수 ID, 확인 토큰, 접수 시각 |
| `POST /v1/report-uploads` | 제보 첨부 업로드 URL 발급 | 만료되는 업로드 URL·첨부키 |
| `GET /v1/reports/{token}` | 제보 처리 상태 확인 | 현재 상태, 상태 변경 시각 |
| `GET /v1/favorites` | 즐겨찾기 조회 | 저장된 출발·목적·경로 정보 |
| `POST /v1/favorites` | 즐겨찾기 저장 | 즐겨찾기 ID |
| `DELETE /v1/favorites/{id}` | 즐겨찾기 삭제 | 삭제 결과 |

경로 응답에 필요한 최소 필드:

```text
승차·하차 managementId
정류장명·번호·방면
내부·외부 노선 ID
표시 버스 번호
승차 정류장까지 도보시간
환승 횟수
데이터 출처
계산 시각
```

도착 응답에 필요한 최소 필드:

```text
routeId
routeNo
arrivalSeconds
previousStopCount
observedAt
live
```

경로 응답과 도착 응답은 갱신 주기가 다르므로 분리한다.

## 7. 보안·개인정보

### 7.1 필수 보안

- [ ] TAGO·지도·경로 API 키를 서버 비밀 저장소에 보관한다.
- [ ] `VITE_` 환경변수에 비밀키를 넣지 않는다.
- [ ] 관리자 인증에 기관 계정과 MFA를 적용한다.
- [ ] 조회자·처리자·승인자·시스템관리자 권한을 분리한다.
- [ ] 세션 쿠키에 `Secure`, `HttpOnly`, `SameSite=Strict`를 적용한다.
- [ ] 상태 변경 요청에 CSRF 방어를 적용한다.
- [ ] 열람·변경·내보내기를 감사 로그에 기록한다.
- [ ] 첨부파일의 확장자·MIME·용량·악성파일을 검사한다.
- [ ] API 호출 제한과 비정상 사용 탐지를 적용한다.
- [ ] 데이터베이스 백업과 실제 복구 훈련을 실시한다.

### 7.2 개인정보 원칙

- 정확한 GPS는 경로 계산 후 장기 저장하지 않는다.
- 목적지 상세 검색어는 기본적으로 보관하지 않는다.
- 음성 원본은 텍스트 변환 후 폐기한다.
- 원본 음성을 저장하려면 별도 동의와 보존기간을 둔다.
- 전화번호·상세주소·얼굴·차량번호 등은 마스킹한다.
- 영구 기기 ID와 지속 위치 추적을 사용하지 않는다.
- 공개 통계에서 소수 사용자를 재식별할 수 있는 조합을 억제한다.
- 제보·첨부·감사 로그별 보존기간과 삭제 정책을 정한다.

## 9. 검증과 출시 조건

### 9.1 데이터·경로 검증

- [ ] 맞은편 정류장 5쌍 이상에서 승차 지점과 방면을 검증한다.
- [ ] 대표 출발–목적지 10건 이상을 실제 지도·현장 정보와 대조한다.
- [ ] 동명 정류장 이름만으로 자동 확정된 사례가 0건이다.
- [ ] 버스가 도보시간보다 먼저 도착해 탈 수 없는 후보를 제외한다.
- [ ] `unknown`을 근거 없이 `no`로 바꾼 사례가 0건이다.
- [ ] `inferred` 외부 ID를 운영 결합에 사용한 사례가 0건이다.
- [ ] API 실패를 추정값으로 감춘 사례가 0건이다.

### 9.2 시민 사용성 검증

65세 이상 사용자 5명 이상이 도움 없이 다음 과업을 수행해야 한다.

1. 버스 메뉴 선택
2. 출발지·목적지 입력
3. 지도·주소로 장소 확인
4. 탈 정류장·방면·도착시간 확인
5. 즐겨찾기 또는 정류장 상태 제보

기록 항목:

- 과업 성공률
- 완료시간
- 도움 요청 횟수
- 잘못 선택한 정류장·장소
- 음성 입력 재시도
- 중도 이탈 지점

### 9.3 접근성·화면 검증

- [ ] 320×461px 실제 사용영역에서 핵심 흐름에 세로 스크롤이 없다.

- [ ] 키보드와 스크린리더로 주요 기능을 사용할 수 있다.
- [ ] iOS·Android 안전영역과 콘텐츠가 겹치지 않는다.
- [ ] 저사양 기기와 느린 네트워크에서 실패 안내가 유지된다.

### 9.4 장애 검증

- [ ] 장소 검색 결과 없음
- [ ] 춘천 밖 장소
- [ ] 대중교통 경로 없음

- [ ] 데이터 배포 실패와 이전 버전 롤백

### 9.5 출시 판정

- [ ] 자동 갱신 전 변경 내역과 승인 단계를 둔다.

### API·백엔드

- [ ] 장소·경로·TAGO 공급자를 서버 어댑터로 연결했다.
- [ ] 시민 API와 관리자 API를 분리했다.
- [ ] 경로와 도착정보 캐시를 분리했다.
- [ ] 공통 오류 코드와 요청 ID를 적용했다.
- [ ] 제보·첨부·처리 이력을 영구 저장한다.

### 시민 앱

- [ ] 장소명·주소·지도를 보고 사용자가 좌표를 확정한다.
- [ ] 탈 정류장 번호와 방면을 함께 표시한다.
- [ ] 실시간 조회 시각과 실패 상태를 표시한다.
- [ ] 즐겨찾기를 열 때 경로와 도착정보를 다시 조회한다.
- [ ] 음성 없이도 모든 기능을 사용할 수 있다.

### 관리자

- [ ] 기관 계정·MFA·역할 권한을 적용했다.
- [ ] 제보 원문과 AI 결과를 구분해 표시한다.
- [ ] 시설 갱신 전에 근거·관측일·검수자를 요구한다.
- [ ] 모든 열람·변경·내보내기를 감사 로그에 남긴다.
- [ ] 데이터 변경을 승인하고 롤백할 수 있다.

### 운영

- [ ] API 오류율·지연·호출량을 모니터링한다.
- [ ] 미매핑·ID 불일치를 검수 큐로 보낸다.
- [ ] 개인정보 보존기간과 삭제 작업을 운영한다.
- [ ] 백업에서 실제로 복구할 수 있음을 검증했다.
- [ ] 공급자 비용·호출 한도·약관 변경을 점검한다.

## 12. 최종 판단

현재 프로젝트를 제로베이스로 다시 만든다면 **화면부터 다시 그리는 것이 우선이 아니다.**

가장 먼저 확정할 것은 다음 순서다.

1. 정류장·노선 데이터 계약
2. 외부 API 공급자와 ID 매핑 방식
3. 시민 API·관리자 API·데이터베이스 구조
4. 대표 경로 검증 기준
5. 제보 처리와 시설 갱신의 행정 책임 구조
6. 그 위에 시민 화면과 관리자 화면 구현

이 순서를 지켜야 화면은 동작하지만 실제 경로와 행정 근거는 불확실한 시연용 제품이 반복되지 않는다.
